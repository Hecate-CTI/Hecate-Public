# R-1029: Java4Shell / Java2Shell CVE-2026-114938 OpenJDK Base64 RCE (Calif) Research

**Topic:** Java4Shell / Java2Shell CVE-2026-114938 OpenJDK Base64 RCE (Calif)

## 1. System Research: How It Works

### Summary
OpenJDK HotSpot's C2 JIT compiler utilizes AVX-512 VBMI intrinsics to accelerate Base64 decoding via the java.util.Base64.Decoder, a process activated when x86-64 CPUs support specific instruction sets (Ice Lake+/Zen 4+). This hardware-accelerated path allows applications to efficiently decode untrusted data in headers or payloads, but contains a memory-corruption vulnerability in the native tail handler for malformed inputs.

### Key Findings
- The vulnerability is triggered by malformed Base64 strings with stray padding characters (e.g., 64 'A's + '='), causing the native decoder to compute a negative output length that BZHI converts into an all-ones store mask, resulting in a 64-byte heap overflow past the logical buffer end.
- The memory corruption occurs silently within the JVM; Java subsequently throws an IllegalArgumentException which may be interpreted by applications as a standard validation error (e.g., HTTP 401), masking the prior heap corruption that enables Remote Code Execution.
- Affected systems include OpenJDK 17.0.6+ and derivatives (Temurin, Corretto, etc.) running on x86-64 hardware with AVX-512F + AVX-512BW + AVX-512VBMI + BMI2 capabilities, while standard Java 8/11, OpenJ9, and ARM64 architectures are not affected.
- Pre-auth RCE has been demonstrated against default configurations of Keycloak, Atlassian Jira/Confluence, Jenkins, and Artifactory via HTTP Basic Authorization or JWT/SAML inputs, while post-auth RCE affects Apache Kafka, Solr, and Elasticsearch.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploit CVE-2026-114938 by sending malformed Base64 data with stray padding characters to trigger a heap out-of-bounds write in OpenJDK's AVX-512 accelerated decoder, potentially leading to pre-auth remote code execution (RCE) or memory disclosure. This technique targets enterprise applications like Keycloak, Jira, and Jenkins that process attacker-controlled Base64 inputs before authentication.

### Key Findings
- The vulnerability affects OpenJDK 17.0.6+ on x8-64 CPUs with AVX-512 VBMI support, allowing heap corruption via specific malformed Base64 strings (e.g., 64 'A's + '=' for OpenJDK 21+).
- Pre-auth RCE has been demonstrated against default configurations of Keycloak, Atlassian Jira/Confluence, JFrog Artifactory, Jenkins, and PingFederate.
- Post-auth RCE is possible in Apache Kafka Broker, Solr, Elasticsearch, Gerrit, and Netflix Spinnaker, while client-side TLS paths can also be exploited.
- Attack vectors include any attacker-controlled Base64 input before authentication, such as HTTP Basic Authorization headers, JWTs, SAML artifacts, file uploads, or network messages.
- Mitigations involve patching to specific OpenJDK versions (e.g., 17.0.21.1) or using JVM flags like -XX:-UseBASE64Intrinsics or -XX:UseAVX=2 for immediate protection.

## 5. Research Synthesis

### Executive Summary
CVE-2026-114938 is a memory-corruption vulnerability in OpenJDK 17.0.6+ HotSpot's AVX-512 VBMI Base64 decoder that triggers heap overflow via malformed padding patterns (e.g., 64×'A'+'='), enabling pre-auth RCE against Keycloak, Jira, Confluence, Jenkins, and Artifactory on Ice Lake+/Zen 4+ x86-64 hardware. The corruption occurs silently before Java throws IllegalArgumentException, masking the exploit in standard HTTP 4xx responses. Detection requires correlating malformed Base64 patterns in Authorization/JWT/SAML inputs with JVM decode exceptions, heap corruption signals (SIGSEGV/hs_err), and anomalous child process execution from affected Java services.

### Recommended Hypothesis
> Adversaries use malformed Base64 strings with stray padding characters in HTTP Authorization headers, JWTs, or SAML artifacts to trigger heap corruption in OpenJDK's AVX-512 decoder intrinsic, achieving pre-authentication remote code execution on enterprise Java applications running on Ice Lake+ or Zen 4+ CPUs.

### Gaps Identified
- TLS-encrypted HTTP traffic prevents inspection of malformed Base64 padding patterns in Authorization headers, JWTs, and SAML artifacts at the network perimeter without inline SSL inspection or endpoint-based request logging configured to capture full header values before application processing.
- Standard application logs may not distinguish IllegalArgumentException from Base64 decode operations versus other validation failures, and JVM crash logs (hs_err_pid*.log) or SIGSEGV events may not be ingested into SIEM/EDR, preventing correlation between decode exceptions and subsequent heap corruption indicators.
- Process telemetry may lack sufficient command-line and environment variable capture to inventory JVM startup flags (-XX:-UseBASE64Intrinsics, -XX:UseAVX=2) or CPU feature detection (AVX-512 VBMI support) across the Java service estate, limiting ability to scope vulnerable instances before observing exploitation attempts.
