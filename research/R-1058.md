## 1. System Research: How It Works

### Summary
VibeShield is a zero-dependency, read-only security scanner CLI and GitHub Action designed for AI-built applications, operating through a six-phase process that includes TLS checks, DNS takeover detection, and database probing. It functions by performing strict read-only operations, such as HEAD requests with specific preconditions, to audit infrastructure components like Supabase tables and Firebase databases without downloading user PII. The tool integrates various static and dynamic analysis rules, including CodeQL, Semgrep, and OWASP Benchmark cells, to transform developer intent into secure code specifications.

### Key Findings
- The scanner utilizes a six-phase methodology that specifically targets Supabase PostgREST tables (up to 20) using strictly read-only HEAD requests with the 'Prefer: count=exact' header, ensuring no user PII is downloaded during the probe.
- Network telemetry includes direct node:tls socket handshakes on port 443 to analyze TLS versions (TLSv1.3 vs weak 1.0/1.1), cipher suites, CA issuers, expiry countdowns, and SAN lists for self-signed or mismatched certificates.
- The tool generates public-facing artifacts such as GitHub Action badges via endpoints like /api/badge.svg which accept domain parameters (e.g., domain=yourapp.com) to display audit scores and grades.
- Security validation capabilities are embedded through CodeQL standard security queries, Semgrep OSS rules, and OWASP BenchmarkPython scan cells specifically targeting path traversal, command injection, and cross-site scripting.

## 5. Research Synthesis

### Executive Summary
A public GitHub repository (zColdWater/vibeshield-cli) references CVE-2025-29927, an improper authorization vulnerability in Vercel Next.js (CVSS 9.3, EPSS 75.27th percentile, VulnCheck-flagged as actively exploited in-the-wild) that enables middleware authentication bypass without user interaction; the repository itself presents as a defensive scanner CLI but embeds CVE-2025-29927 detection logic that structurally mirrors exploitation probes (parameterized URL inputs, Supabase table enumeration, TLS fingerprinting). No local telemetry has been mapped to this behavior, and the repository's exploit fidelity has not been independently verified, so findings are currently inconclusive pending workspace evidence.

### Recommended Hypothesis
> Adversaries use CVE-2025-29927 Next.js middleware authorization bypass — potentially aided by public PoC tooling referencing vibeshield-cli or equivalent — to circumvent authentication controls on internet-facing Next.js applications and gain unauthorized access to protected API routes or downstream cloud resources (T1190), targeting environments running unpatched Vercel Next.js middleware.

### Gaps Identified
- Next.js middleware execution and header-level request inspection are not surfaced in standard WAF or web server access logs; the bypass works by injecting or manipulating the 'x-middleware-subrequest' header, which is typically stripped or not logged by default reverse-proxy and CDN configurations, leaving the authentication bypass invisible in most log pipelines without explicit header capture and forwarding enabled.
- The six-phase probe pattern emitted by vibeshield-cli (HEAD requests to Supabase PostgREST table paths, direct node:tls socket handshakes on port 443, parameterized URL inputs to endpoints like /?url= and /api/badge.svg) is structurally indistinguishable from legitimate scanner or CI/CD audit traffic without behavioral baselining of outbound request cadence, User-Agent strings, and request header combinations — no telemetry mapping has been completed for the local estate, leaving coverage unknown.
- Server-Side Request Forgery (SSRF) exploitation via the /?url= parameter pattern identified in the repository would route malicious outbound requests through the application server's network identity; without egress filtering logs, IMDS access telemetry (e.g., requests to 169.254.169.254), or internal service call auditing, post-exploitation SSRF pivots to cloud metadata services or internal APIs would not be observable in current described telemetry.
