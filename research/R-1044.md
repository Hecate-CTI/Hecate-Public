## 1. System Research: How It Works

### Summary
runc is a container runtime that manages the lifecycle of Linux containers, including handling mount operations such as 'maskedPaths' to restrict access to specific host files. During container creation, it processes these masks to ensure certain paths are hidden or read-only within the container's root filesystem.

### Key Findings
- The vulnerability affects runc versions up to 1.2.7, 1.3.0-rc.1 through 1.3.1, and 1.4.0-rc.1 through 1.4.0-rc.2, allowing container escape via improper link resolution in the maskedPaths feature.
- Exploitation involves a race condition where an attacker repeatedly replaces /dev/null with a symbolic link to /proc/sys/kernel/core_pattern during container initialization, tricking runc into bind-mounting writable host paths.
- The exploit automation requires replacing rootfs/dev/null in a tight loop for approximately 20 seconds to successfully trigger the mount race and achieve host code execution.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries can exploit CVE-2025-31133, a high-severity container escape vulnerability in runc's maskedPaths feature, by abusing mount race conditions to replace /dev/null with symbolic links during container creation. This technique allows attackers to mount arbitrary host paths or disable LSM labels like AppArmor, effectively bypassing security controls and gaining unauthorized host access.

### Key Findings
- CVE-2025-31133 is a high-severity (CVSS 7.3-8.6) container escape vulnerability in runc affecting versions 1.2.7 and below, 1.3.0-rc.1 through 1.3.1, and 1.4.0-rc.1.
- The exploit relies on a race condition where the attacker repeatedly deletes rootfs/dev/null to replace it with a symlink pointing to sensitive host files like /proc/sys/kernel/core_pattern.
- Multiple public Proof-of-Concept (PoC) repositories exist, including 'EscapeArmed' which acts as a scanner and prover using harmless canary probes, and others that demonstrate the actual escape mechanism.
- The vulnerability allows adversaries to bypass security mitigations such as AppArmor by disabling LSM labels, making it a potent technique for combining with other attacks.
- The issue is fixed in runc versions 1.2.8, 1.3.3, and 1.4.0-rc.3; organizations must verify their runtime versions to assess exposure.
- Detection tools like Falco, Kyverno, and SARIF outputs are being referenced in research contexts to identify or prevent these escape primitives.

## 5. Research Synthesis

### Executive Summary
CVE-2025-31133 is a high-severity runc container escape vulnerability exploiting mount race conditions in the maskedPaths feature, where attackers repeatedly replace /dev/null with symlinks to /proc/sys/kernel/core_pattern during container initialization to achieve host code execution. Public PoCs exist including EscapeArmed (a scanner/prover tool) and functional exploits requiring ~20 seconds of tight-loop symlink replacement to win the race. The source intelligence describes only a scanning tool repository with no observed attacker activity; actual exploitation would require detecting the race condition behavior, symlink manipulation, and subsequent host-level actions within containerized environments.

### Recommended Hypothesis
> Adversaries use mount race conditions during container creation to replace /dev/null with symbolic links pointing to host paths like /proc/sys/kernel/core_pattern, achieving container escape and host code execution on runc-based container platforms

### Gaps Identified
- Container runtime mount operations during initialization are typically not logged with sufficient granularity to detect rapid symlink replacement attempts targeting /dev/null in the rootfs, particularly the tight-loop behavior occurring within the ~20 second exploitation window
- File system monitoring within ephemeral container rootfs directories during the container creation phase may not capture symlink creation/deletion events at the frequency required to detect race condition exploitation attempts before the container becomes operational
- Correlation between container creation events and subsequent writes to sensitive host paths like /proc/sys/kernel/core_pattern or AppArmor profile modifications may not exist if container runtime telemetry and host-level file integrity monitoring operate in separate visibility domains

### Key Findings
- Hypothesis: Adversaries use mount race conditions during container creation to replace /dev/null with symbolic links pointing to host paths like /proc/sys/kernel/core_pattern, achieving container escape and host code execution on runc-based container platforms
- Gap: Container runtime mount operations during initialization are typically not logged with sufficient granularity to detect rapid symlink replacement attempts targeting /dev/null in the rootfs, particularly the tight-loop behavior occurring within the ~20 second exploitation window
- Gap: File system monitoring within ephemeral container rootfs directories during the container creation phase may not capture symlink creation/deletion events at the frequency required to detect race condition exploitation attempts before the container becomes operational
- Gap: Correlation between container creation events and subsequent writes to sensitive host paths like /proc/sys/kernel/core_pattern or AppArmor profile modifications may not exist if container runtime telemetry and host-level file integrity monitoring operate in separate visibility domains
- Focus: Query container runtime audit logs (containerd, CRI-O, Docker) for rapid container creation failures or repeated initialization attempts within short time windows, correlating with file system events showing /dev/null manipulation or symlink creation in container rootfs paths
- Focus: Monitor host-level writes to /proc/sys/kernel/core_pattern, /proc/sys/kernel/modprobe, and LSM configuration paths (AppArmor, SELinux) originating from container runtime processes (runc, crun) or occurring temporally adjacent to container lifecycle events
- Focus: Identify containers running with elevated privileges (privileged mode, CAP_SYS_ADMIN) or custom seccomp/AppArmor profiles that perform mount operations, particularly those accessing /proc or /sys host paths, as these represent higher-risk escape opportunities when combined with the vulnerability
