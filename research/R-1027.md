## 1. System Research: How It Works

### Summary
Next.js middleware is designed to handle requests such as authentication checks before they reach the main application logic. However, in vulnerable versions (11.1.4 through 15.x), the framework incorrectly trusts the `x-middleware-subrequest` header even when it originates from an external client, allowing attackers to bypass these authorization controls.

### Key Findings
- The vulnerability allows for authentication bypass by injecting a specially crafted `x-middleware-subrequest` header into HTTP requests sent by external clients.
- The issue affects Next.js versions 11.1.4 through 13.5.6, 14.x prior to 14.2.25, and 15.x prior to 15.2.3.
- Public Proof of Concept (PoC) repositories exist, such as 'Seif-Abdelhamid/nextjs-middleware-bypass-lab' and 'DanielHallbro/CVE-2025-29927-Nextjs-Bypass-PoC', providing reproducible labs and detection toolkits for this specific CVE.
- The vulnerability is classified under MITRE ATT&CK technique T1190 (Exploit Public-Facing Application) and is categorized as an Authentication Bypass.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries can abuse CVE-2025-29927 to bypass Next.js authorization mechanisms by exploiting a flaw in the internal HTTP header handling of versions prior to 13.5.9, potentially gaining unauthorized access to admin panels and sensitive data. This vulnerability is classified as an Authentication Bypass with a high CVSS score of 9.1, enabling unauthenticated attackers to circumvent middleware checks.

### Key Findings
- The vulnerability affects Next.js versions prior to 13.5.9 and allows unauthenticated attackers to bypass authorization by manipulating specific internal HTTP headers.
- Multiple proof-of-concept repositories exist on GitHub (e.g., Seif-Abdelhamid/nextjs-middleware-bypass-lab, DanielHallbro/CVE-2025-29927-Nextjs-Bypass-PoC) demonstrating the exploit mechanics.
- Security vendor Stormshield Network Security has developed specific IPS signatures to detect and block exploitation attempts of CVE-2025-29927.
- Successful exploitation can lead to compromise of the admin panel, allowing webpages to be edited and sensitive information to be accessed.
- Mitigation requires upgrading Next.js to version 13.5.9 or later to resolve the middleware bypass weakness.

## 5. Research Synthesis

### Executive Summary
CVE-2025-29927 is an authentication bypass in Next.js middleware (versions 11.1.4-13.5.6, 14.x<14.2.25, 15.x<15.2.3) exploitable via injected `x-middleware-subrequest` headers, with public PoCs available and VulnCheck reporting active in-the-wild exploitation (EPSS 99.22%). The source intelligence is a PoC repository publication, not observed attacker activity; hunting requires identifying Next.js applications in scope, verifying web proxy/WAF telemetry captures custom headers in request logs, and correlating suspicious header patterns with authentication state changes. No telemetry was mapped because the source describes capability research rather than adversary behavior observed in the workspace.

### Recommended Hypothesis
> Adversaries use HTTP requests containing crafted `x-middleware-subrequest` headers against vulnerable Next.js applications (versions 11.1.4-13.5.6, 14.x<14.2.25, 15.x<15.2.3) to bypass middleware authentication checks and gain unauthorized access to protected resources

### Gaps Identified
- Web proxy, WAF, and application logs may not capture or retain custom HTTP headers (specifically `x-middleware-subrequest`) in request telemetry, preventing detection of the exploitation vector even if requests reach vulnerable endpoints
- Asset inventory may lack visibility into Next.js framework versions deployed on public-facing web applications, preventing scoped queries against only vulnerable targets and increasing false negative risk if broad header searches are infeasible
- Authentication success events from Next.js applications may not correlate with request headers or distinguish between legitimate middleware-processed requests and bypassed authentication flows, obscuring post-exploitation access patterns

### Key Findings
- Hypothesis: Adversaries use HTTP requests containing crafted `x-middleware-subrequest` headers against vulnerable Next.js applications (versions 11.1.4-13.5.6, 14.x<14.2.25, 15.x<15.2.3) to bypass middleware authentication checks and gain unauthorized access to protected resources
- Gap: Web proxy, WAF, and application logs may not capture or retain custom HTTP headers (specifically `x-middleware-subrequest`) in request telemetry, preventing detection of the exploitation vector even if requests reach vulnerable endpoints
- Gap: Asset inventory may lack visibility into Next.js framework versions deployed on public-facing web applications, preventing scoped queries against only vulnerable targets and increasing false negative risk if broad header searches are infeasible
- Gap: Authentication success events from Next.js applications may not correlate with request headers or distinguish between legitimate middleware-processed requests and bypassed authentication flows, obscuring post-exploitation access patterns
- Focus: Enumerate public-facing Next.js applications in scope via asset inventory, banner grabbing, or JavaScript framework fingerprinting in web traffic, then correlate with package.json or dependency audit data to identify vulnerable version ranges (11.1.4-13.5.6, 14.x<14.2.25, 15.x<15.2.3)
- Focus: Query web proxy, WAF, and HTTP server logs for requests containing `x-middleware-subrequest` header (case variations) directed at identified Next.js endpoints, filtering for external source IPs and correlating with HTTP 200/30x responses to protected paths that should require authentication
- Focus: Baseline normal authentication patterns (session establishment, token issuance) for Next.js applications, then hunt for anomalous access to admin/protected routes lacking corresponding authentication events or originating from IPs with no prior session history within a temporal window
