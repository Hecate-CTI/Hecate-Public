## 1. System Research: How It Works

### Summary
Optimizely Web Experimentation operates by injecting a JavaScript snippet from Optimizely’s Content Delivery Network (cdn.optimizely.com) into customer websites to dynamically modify visitor experiences and collect conversion data. This mechanism allows for real-time A/B testing and personalization without requiring direct modifications to the underlying website code, effectively altering the client-side state via external script execution.

### Key Findings
- The system relies on a JavaScript snippet loaded from Optimizely-hosted assets (specifically cdn.optimizely.com) that dynamically applies changes to visitors' browsers based on experimentation logic.
- Network traffic involves data collection regarding visitor behavior and conversions, which is transmitted to the platform for processing by the 'Stats Engine' to determine test effectiveness.
- The architecture allows for customization via API calls and supports multiple snippet configurations per project, enabling complex multivariate testing strategies across web and edge environments.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploited an external control of critical state data vulnerability (CVE-2026-132224) in Optimizely Web Experimentation's account signup flow to gain unauthorized write access to the Project JavaScript field. This allowed them to inject malicious scripts, such as card skimmers and iOS exploit kits, which were then distributed to victims via Optimizely-hosted assets and executed in user browsers visiting compromised customer websites.

### Key Findings
- The attack vector was a flaw in the account signup flow that permitted unauthorized modification of the Project JavaScript field, enabling the injection of attacker-controlled code.
- Malicious scripts were served from Optimizely’s CDN (cdn.optimizely.com) or customer domains, leveraging implicit trust in the platform to deliver payloads like card skimmers and iOS exploit kits.
- The compromise affected at least 178 high-profile organizations, including CNN, BBC, and Zoom, indicating a widespread supply chain impact rather than isolated incidents.
- The malicious code was executed client-side in browsers of visitors to affected customer websites, effectively turning Optimizely snippets into a delivery mechanism for stealers and exploits.
- Optimizely responded by fixing the vulnerability, removing injected code, revoking tokens, resetting access, and ending active sessions for affected accounts.

## 5. Research Synthesis

### Executive Summary
CVE-2026-132224 (CISA KEV, added 2026-11-24) describes an external control of critical state data vulnerability in Optimizely Web Experimentation's account signup flow that, per VulnCheck, is confirmed actively exploited in-the-wild; successful exploitation yields attacker-controlled JavaScript injected into the Project JavaScript field and served to end-user browsers via cdn.optimizely.com, constituting a supply-chain JavaScript injection primitive. The attack surface is entirely SaaS-side and CDN-delivery-side: no server-side or endpoint execution by the adopter's infrastructure is described, meaning detection must pivot to outbound CDN fetch behavior, browser-side script content integrity, and Optimizely control-plane audit logs rather than traditional endpoint telemetry. EPSS scores this at 0.41% exploit probability (35.8th percentile) — a low calibrated signal that conflicts with VulnCheck's in-the-wild confirmation and CISA KEV listing, so the KEV/VulnCheck evidence should be weighted over EPSS for prioritization; EPSS and numeric scores are uncalibrated and not treated as probabilities here.

### Recommended Hypothesis
> Adversaries exploit the account signup flow authorization flaw in Optimizely Web Experimentation (CVE-2026-132224) to write attacker-controlled JavaScript into victim organizations' Project JavaScript fields, causing malicious payloads (e.g., card skimmers, exploit kits) to be distributed from cdn.optimizely.com and executed in the browsers of visitors to affected customer websites.

### Gaps Identified
- No Optimizely control-plane audit log telemetry is described as available or ingested — specifically, logs recording Project JavaScript field modification events, account signup activity, or API write operations against Optimizely project configurations. Without these logs, unauthorized writes to the Project JavaScript field cannot be distinguished from legitimate A/B test deployments, leaving the initial exploitation step entirely blind regardless of endpoint or network sensor coverage.
- The malicious payload is delivered as a CDN-hosted JavaScript asset from cdn.optimizely.com, a domain that is broadly trusted and likely allowlisted in proxy, firewall, and content security policy configurations. Standard network egress telemetry will record the fetch as a benign CDN request; without Sub-Resource Integrity (SRI) hash validation telemetry, browser Content Security Policy violation reports, or JavaScript content inspection at the proxy layer, the payload content itself is opaque to hunt queries — fetch success alone does not distinguish clean from tampered script.
- Client-side browser execution telemetry (e.g., browser process network connections, DOM mutation events, form field exfiltration attempts, or JavaScript runtime behavior indicative of skimmer activity) is not mapped as an available data source in this environment. Because the entire attack chain terminates in the visitor's browser rather than on a monitored endpoint, behavioral evidence of skimmer execution — such as data being POSTed to attacker-controlled infrastructure — requires browser telemetry, endpoint EDR coverage of browser child processes, or proxy egress inspection that is not confirmed as available.
